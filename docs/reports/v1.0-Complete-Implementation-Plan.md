## P0-LLM: LLM 驱动意图编排器

### 目标

将当前 RulePlanner（20 个关键词匹配）替换为 LLM 驱动的智能意图识别和任务规划。

### 当前状态

- `planner/planner.go:26-28` — `Planner` 接口已定义，`Plan(ctx, PlannerInput) (*OrchestrationPlan, error)`
- `planner/rule_planner.go` — RulePlanner 实现，仅关键词匹配
- `handler_run_stream.go:116` — 硬编码 `planner.NewRulePlanner(availableAgentNames)`
- `pkg/runtime/model/` — Anthropic/OpenAI Provider 已就绪，注册在 `init()` 中
- `pkg/runtime/registry/model.go` — `CreateAndRegisterModel()` 可创建 Model 实例

### 协议影响

```
LLMPlanner 内部调用 adk.Model.Generate()（非流式，获取结构化 JSON）
    ↓
解析 JSON → 构建 plan.OrchestrationPlan
    ↓
PlanValidator 校验（13 条规则不变）
    ↓
Executor 不变（SingleExecutor / OrderedParallelExecutor）
    ↓
AG-UI SSE 事件不变
```

**A2A 协议无影响** — LLMPlanner 在 Orchestrator 内部运行，不涉及 A2A 通信。
**AG-UI 协议影响** — 新增 `STATE_UPDATE` 事件携带 `intent` 和 `reasoning` 字段，前端展示编排推理过程。

**新建文件:** `services/orchestrator/planner/planner_llm.go`

```go
package planner

// PlannerLLM 编排器专用 LLM 客户端
// 非流式调用，获取结构化 JSON 输出
// 支持 Anthropic 和 OpenAI 两种 Provider

type PlannerLLMConfig struct {
    Provider string // "anthropic" | "openai"
    APIKey   string // 从环境变量读取
    Model    string // 默认 "claude-haiku-4-5-20251001"（轻量模型，降低成本）
    BaseURL  string
}

type PlannerLLM struct {
    cfg    PlannerLLMConfig
    client *http.Client // 30s 超时
}

func NewPlannerLLM(cfg PlannerLLMConfig) *PlannerLLM

// Generate 调用 LLM，返回纯文本（JSON），自动处理 markdown 包裹
func (l *PlannerLLM) Generate(ctx context.Context, systemPrompt, userPrompt string) (string, error)
```

关键设计：
- 使用独立的轻量 HTTP Client（30s 超时），不依赖 `pkg/runtime/registry`（避免循环依赖或启动顺序问题）
- 支持 Anthropic Messages API 和 OpenAI Chat Completions API
- 自动剥离 LLM 返回的 ```json ... ``` 包裹
- 错误时返回明确错误信息，由上层 fallback

#### Step 0.2: 新增 LLMPlanner 实现 Planner 接口

**新建文件:** `services/orchestrator/planner/llm_planner.go`

```go
package planner

// LLMPlanner 使用 LLM 分析用户意图并生成执行计划
type LLMPlanner struct {
    llm        *PlannerLLM
    registry   AgentRegistry // 接口：Get(name) + Names()
}

// AgentRegistry 是 Planner 所需的注册表抽象（最小接口）
type AgentRegistry interface {
    Get(name string) (registry.AgentEndpoint, bool)
    Names() []string
}

func NewLLMPlanner(llm *PlannerLLM, reg AgentRegistry) *LLMPlanner

func (p *LLMPlanner) Plan(ctx context.Context, input PlannerInput) (*plan.OrchestrationPlan, error)
```

**Plan() 方法流程:**

```
1. buildSystemPrompt(agents) → 系统提示（Agent 列表、能力、输出格式约束）
2. buildUserPrompt(input)   → 用户提示（历史消息摘要、当前消息）
3. llm.Generate(ctx, systemPrompt, userPrompt)
4. 解析 JSON → ExecutionPlanJSON
5. validateAndConvert → plan.OrchestrationPlan
6. 如果 LLM 失败或 JSON 非法 → fallbackPlan()（调用 RulePlanner 兜底）
```

**系统提示模板（buildSystemPrompt）:**

```
You are an intent orchestrator for a multi-agent platform. Your job is to analyze the user's request and create an execution plan.

## Available Agents
{for each agent in registry}:
- name: {agent.Name}
  description: {agent.Description}
  capabilities: {agent.CapabilityIDs}
  outputModes: {agent.OutputModes}

## Execution Strategies
- "single": one agent handles the entire request
- "ordered_parallel": multiple agents work on independent sub-tasks in order

## Rules
1. For code/backend requests → use code-agent
2. For web UI/frontend/page requests → use web-agent
3. If the request needs BOTH backend code AND frontend UI → use "ordered_parallel" with both agents
4. web-agent should run BEFORE code-agent in ordered_parallel (frontend first, then backend)
5. Each task's capabilityIds MUST be from the agent's actual capabilities
6. Each task's expectedOutputs MUST be from the agent's actual outputModes
7. timeoutMs: 30000 for simple tasks, 60000 for complex tasks
8. riskLevel: always "low" for v1.0
9. taskContent should rephrase the user's request specifically for the target agent

## Output Format
Return ONLY a JSON object with this exact structure (no markdown, no explanation):
{
  "intent": "brief summary of what the user wants",
  "reasoning": "brief explanation of why this strategy and agents were chosen",
  "strategy": "single" | "ordered_parallel",
  "tasks": [
    {
      "agentName": "exact-agent-name",
      "capabilityIds": ["capability-from-agent"],
      "taskContent": "rephrased request for this specific agent",
      "expectedOutputs": ["output-mode-from-agent"],
      "priority": 1
    }
  ]
}
```

**JSON 解析结构体:**

```go
type llmPlanResponse struct {
    Intent    string           `json:"intent"`
    Reasoning string           `json:"reasoning"`
    Strategy  string           `json:"strategy"`
    Tasks     []llmTaskPlan    `json:"tasks"`
}

type llmTaskPlan struct {
    AgentName       string   `json:"agentName"`
    CapabilityIDs   []string `json:"capabilityIds"`
    TaskContent     string   `json:"taskContent"`
    ExpectedOutputs []string `json:"expectedOutputs"`
    Priority        int      `json:"priority"`
}
```

**validateAndConvert 逻辑:**

```go
func (p *LLMPlanner) validateAndConvert(resp *llmPlanResponse, input PlannerInput) (*plan.OrchestrationPlan, error) {
    // 1. 验证 strategy 合法
    // 2. 验证 tasks 非空
    // 3. 对每个 task，验证 agentName 在 registry 中存在
    //    如果不存在 → 尝试模糊匹配，失败则用默认 agent
    // 4. 验证 capabilityIds 是 agent 实际能力的子集
    // 5. 构建 OrchestrationPlan，填充所有必填字段：
    //    - PlanID, RunID, ConversationID, Version="v1"
    //    - PlanningMode=input.PlanningMode, IntentSummary
    //    - Aggregation, Fallback, Validation
    //    - 每个 TaskPlan 的 TimeoutMs=30000, RiskLevel="low"
    return plan, nil
}
```

**fallbackPlan 逻辑:**

```go
func (p *LLMPlanner) fallbackPlan(input PlannerInput) *plan.OrchestrationPlan {
    // 直接委托给 RulePlanner.Plan()
    rulePlanner := NewRulePlanner(input.AvailableAgents)
    plan, err := rulePlanner.Plan(context.Background(), input)
    if err != nil {
        // 终极兜底：默认 code-agent
        return defaultCodeAgentPlan(input)
    }
    return plan
}
```

#### Step 1.3: 确保 ADK Runner 的 Tool Use 循环正常工作

当前 mock Agent 永远返回 `FinishStop`（不触发 Tool Call 循环）。LLMAgent 会返回 `FinishToolUse`，Runner 需要正确执行：

```
User Message → Agent.Generate()
  → FinishToolUse: [ToolCallPart{generate_code_snippet, args}]
  → Runner 执行 Tool
  → ToolResultPart
  → Agent.Generate()（第二次，带 Tool Result）
  → FinishStop: [TextPart{final response}]
```

需要验证：
- `pkg/adk/runner.go` 的循环逻辑（第 ~85-135 行）正确
- `pkg/adk/llmagent.go` 的 `transferTool` 逻辑不影响正常 Tool Use
- 当前 Runner 的 `executeTools()` 方法（第 ~200 行）能正确执行 code-agent 和 web-agent 注册的 Tool

#### Step 1.4: 处理 Artifact 输出

LLM 生成代码/HTML 后，需要将结果包装为 Artifact 以便前端展示。

**方案 A（推荐）:** 在 Agent 的 Tool 实现中，`Execute()` 返回的 `ToolResult.Content` 已包含代码/HTML。Runner 的 Tool Call 循环会自动将 ToolResult 传递给 LLM，LLM 可以在最终回复中引用。同时，在 Tool 的 `Execute()` 中标记 artifact 元数据：

```go
// 不修改 ADK 核心，而是在上层（Runner 或 Translator 中）识别 tool result 中的 artifact 内容
```

**方案 B:** 在 Agent System Prompt 中指示 LLM 使用特定格式输出，由 Gateway Translator 解析：

```
When you generate code, also include an artifact annotation:
{artifact:code, language:go, title:main.go}
```

**建议先采用方案 A**，因为现有的 Translator 已经支持 `Actions.ArtifactDelta` 路径。

#### Step 4.1: A2A Dispatcher 增加重试

**修改文件:** `services/orchestrator/dispatcher/a2a_dispatcher.go`

```go
// DispatchWithRetry 带重试的派发
func (d *A2ADispatcher) DispatchWithRetry(
    ctx context.Context,
    input DispatchInput,
    maxRetries int,           // 默认 2
    backoff time.Duration,     // 初始退避 1s
) (*DispatchResult, error) {
    var lastErr error
    for attempt := 0; attempt <= maxRetries; attempt++ {
        if attempt > 0 {
            // 指数退避：1s, 2s, 4s
            wait := backoff * time.Duration(1<<(attempt-1))
            select {
            case <-ctx.Done():
                return nil, ctx.Err()
            case <-time.After(wait):
            }
        }
        result, err := d.Dispatch(ctx, input)
        if err == nil {
            return result, nil
        }
        lastErr = err
        log.Printf("dispatcher: attempt %d/%d for %s failed: %v",
            attempt+1, maxRetries+1, input.AgentName, err)
    }
    return nil, fmt.Errorf("dispatch failed after %d retries: %w", maxRetries+1, lastErr)
}
```

func (s *Server) handleRunStream(w http.ResponseWriter, r *http.Request) {
    // 1. 解析请求（同 handleRun）
    // 2. 验证 sessionId / message（同 handleRun）
    // 3. 设置 SSE 响应头：
    w.Header().Set("Content-Type", "text/event-stream")
    w.Header().Set("Cache-Control", "no-cache")
    w.Header().Set("Connection", "keep-alive")
    flusher := w.(http.Flusher)

    // 4. 调用 runner.Run()
    for event, err := range s.runner.Run(ctx, sessionID, content) {
        if err != nil {
            writeSSEEvent(w, flusher, "error", eventDTO{...})
            return
        }
        // 5. 逐个 Event 转为 eventDTO 并写入 SSE
        dto := toEventDTO(event)
        writeSSEEvent(w, flusher, "event", dto)
        flusher.Flush()

        if event.Final {
            break
        }
    }
}

    fmt.Fprintf(w, "event: %s\ndata: %s\n\n", eventType, jsonData)
}

## P7-Parallel: 真正并行执行

### 目标

当前 OrderedParallelExecutor 虽然名字里有 "parallel"，但实际是串行执行（按优先级顺序依次调用 Agent）。需要实现真正的 goroutine 并行执行，同时保证前端事件顺序（web-agent 输出在前，code-agent 输出在后）。

### 实现方案

因为 AG-UI 协议要求事件有序（web-agent 的输出必须在 code-agent 之前到达前端），真正的并行执行策略为：

1. **并行派发**：同时向两个 Agent 发送 A2A 请求
2. **缓冲结果**：每个 Agent 的输出收集到独立的 buffer 中
3. **顺序输出**：按优先级排列顺序，依次 flush 每个 Agent 的 buffer 到 SSE

### 实现步骤

#### Step 7.1: 新增 ParallelExecutor

**新建文件:** `services/orchestrator/executor/parallel_executor.go`

```go
type ParallelExecutor struct {
    registry   AgentRegistry
    dispatcher AgentDispatcher
}

func (e *ParallelExecutor) Execute(ctx context.Context, p *plan.OrchestrationPlan, msgID string) ([]ExecutionEvent, error) {
    // 1. 验证 plan
    // 2. 按优先级排序 tasks
    // 3. 为每个 task 创建 goroutine：
    //    - 派发到 Agent
    //    - 收集结果到 channel
    // 4. 等待所有 goroutine 完成（或超时/错误）
    // 5. 按优先级顺序组装事件（先 web-agent，后 code-agent）
    // 6. 聚合摘要

    type taskResult struct {
        task  plan.TaskPlan
        text  string
        err   error
        index int
    }

    results := make(chan taskResult, len(tasks))
    for i, task := range tasks {
        go func(t plan.TaskPlan, idx int) {
            input := dispatcher.DispatchInput{...}
            result, err := e.dispatcher.Dispatch(ctx, input)
            results <- taskResult{t, result.Text, err, idx}
        }(task, i)
    }

    // 收集结果，按 index 排序
    var ordered []taskResult
    for i := 0; i < len(tasks); i++ {
        select {
        case r := <-results:
            ordered = append(ordered, r)
        case <-ctx.Done():
            // 超时处理
        }
    }
    sort.Slice(ordered, func(i, j int) bool { return ordered[i].index < ordered[j].index })

    // 按排序后的顺序生成事件
    var events []ExecutionEvent
    for _, r := range ordered {
        events = append(events, buildMessageEvents(r)...)
    }
    events = append(events, buildSummaryEvent(ordered))
    events = append(events, buildRunFinishedEvent())
    return events, nil
}
```

#### Step 7.2: 注册 ParallelExecutor
