| 领域 | 是否符合 | 等级 |
|------|----------|------|
| single_chat | **基本符合**，但 plan_only JSON 解析脆弱 | P0 bug |

| 是否存在规则路由风险 | **存在** — MainAgent 是纯关键词匹配，RulePlanner 也按关键词选 Agent | P1 |

### 最终判语

> **基本符合但有 P0 实现 bug。**
>
> 架构骨架正确：三条 executionPath 已落地，ACTIVITY_SNAPSHOT 已替换 confirm_plan TOOL_CALL，planOwner 标识正确，participant boundary 有校验框架。
> 但存在 4 个 P0 实现 bug（plan_only JSON 解析、registerPending 时序导致 502、Gateway 错误码吞噬、sequential 被误拦截）和 2 个 P1 架构 gap（MainAgent 关键词路由、Contract 未更新）。
> 这些是**实现层面可修复的问题**，不需要回滚或重构架构。

### 四) main_agent_orchestration

**文件:** `services/orchestrator/planner/main_agent.go`

MainAgent 是纯关键词匹配器：

```go
var capabilityKeywords = map[string][]string{
    "code-agent":     {"code", "api", "server", "backend", "go", ...},
    "web-agent":      {"web", "frontend", "page", "ui", "html", ...},
    "document-agent": {"document", "doc", "report", "write", ...},
}

func (m *MainAgent) Plan(_ context.Context, input PlannerInput) (*plan.OrchestrationPlan, error) {
    userText := strings.ToLower(input.UserMessage)
    scores := m.scoreAgents(userText)  // 关键词命中计数
    // score >= 3 → required
    // score >= 2 → selected
}
```

**符合性评估:** PARTIAL
- 是 Orchestrator 内部组件，不在 StaticAgentRegistry ✅

**偏差:**

### 七) HITL 确认链路和 502 根因

**三重合致因:**

**根因 1: registerPending 时序** (P0)
- `emitActivitySnapshot()` 在行 329/1130
- `registerPending()` 在行 344/1144
- ACTIVITY_SNAPSHOT 先发送到前端，**之后**才注册 hitlChans
- 若用户在 registerPending 完成前点击 Approve → Orchestrator 返回 404 → Gateway 转 502

**根因 2: Gateway 错误码吞噬** (P0)
- `handler_hitl.go:65-72`: ConfirmRun 返回的 `fmt.Errorf` 不实现 `StatusCode()`
- client.go:449-452: `return fmt.Errorf("orchestrator confirm returned status %d: %s", ...)`
- 所有 Orchestrator 错误 (404/409/401) → Gateway 一律返回 502 "HITL confirmation failed"

**根因 3: Gateway HITLConfirmRequest 缺少 SelectedParticipants** (P0)
- Gateway client.go:410-418 的 struct **缺少** `SelectedParticipants []string` 字段
- Orchestrator handler_hitl.go:14-25 **有**此字段
- 前端发送的 `selectedParticipants` 被 Gateway 的 `json.Marshal` 静默丢弃

**符合性评估:** NON-COMPLIANT — 三个 P0 bug 叠加。

### 八) plan_only JSON 失败根因

**根因: 无 markdown fence 剥离** (P0)

`handler_run_stream.go:1012 和 1220`:
```go
if err := json.Unmarshal([]byte(planResult.Text), &agentPlan); err != nil {
    s.emitErrorEvent(w, flusher, runID, "ORCHESTRATOR_PLAN_PARSE_FAILED", ...)
}
```

- 直接 `json.Unmarshal` 原始 LLM 输出
- 无 `stripMarkdownFences` / `extractJSON` 预处理
- `_archived/planner_llm.go:255` 有此函数但不在当前编译路径
- LLM 常在 JSON 外包 ```` ```json ... ``` ```` → `json.Unmarshal` 失败

**加重因素:**
- Agent 的 plan_only 提示词说 "Return ONLY a JSON object" 但无 API-level `response_format: json_object` 强制
- 无 JSON schema 校验
- plan_only 解析用匿名 struct 在代码中重复两次 (行 999-1011, 1207-1218)

**符合性评估:** NON-COMPLIANT — P0 bug。
