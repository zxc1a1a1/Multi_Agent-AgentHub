图中实线是当前主链路；“消息队列”不在当前主链路中——Redis 目前承担 cache/relay，尚未启用 Redis Streams 消费组；Kafka/NATS 未部署。

数据所有权

  • MySQL 是唯一权威：run 状态、审批、取消、租约/fencing、事件 journal、outbox、route_decisions、tool ledger。
  • Redis 是辅助：短期缓存/跨实例信号加速；Redis 丢失不能让 MySQL 事实丢失。
  • Artifact 是二元结构：元数据（artifact_store）与二进制（object store / 本地 blob）分开；渲染制品带 checksum。
  • AG-UI SSE 是前端运行面：Gateway 负责将内部事件映射成公开事件，内部 A2A/工具错误不能原样透传。

Gateway → Orchestrator 内部面

入口作用

/internal/orchestrator/hitl/confirm确认/修订；跨实例 durable fallback

/internal/orchestrator/metrics*运营、路由与 Prometheus 指标
边界：这些 /internal/* 只允许服务间调用；Nginx 明确拒绝公开暴露。前端只认 /api/*。

联调关键机制

  • POST SSE：不是 EventSource，因为需要携带用户消息；前端用 fetch 读取流并逐事件喂给 reducer。
  • run 生命周期：RUN_STARTED → plan/activity → agent turns → RUN_FINISHED；错误也必须按安全错误事件收敛。
  • 幂等：Gateway 先记录 chat request；相同 requestId 返回冲突/已接受，避免重复派发。
  • 恢复：Gateway status/events 读 MySQL；Gateway 投影 worker 按 offset 重建助手消息，避免只依赖 SSE 内存缓存。
  • 认证 artifact：前端图片与下载用带 Authorization 的 fetch，而不是裸 <img src>；避免 auth 模式下 401。

05一条用户消息如何处理

  1. 前端组装请求：选中的 Agent、mentions、requestedPath、pinnedMessageIds、replyTo/quote、contextMessages 被放入 POST /api/chat。
  2. Gateway 校验与幂等：校验 conversation/message；生成/读取 requestId；记录 chat request；生成 runId；推送 SSE 头。
  3. 派生路径：先看显式 requestedPath；否则按 Agent 选择派生：auto/空 → main_agent_orchestration，单 Agent → single_chat，多 Agent/mentions → group_chat。
  4. Gateway → Orchestrator：通过内部 SSE 转发；携带 Bearer 服务 token、runId、conversationId、selectedAgentNames、mentions、pinned 等。
  5. Orchestrator 校验边界：再次派生 executionPath；与 Gateway 传入不一致直接拒绝；校验 Agent 是否在注册表/边界内。
  6. MainAgent 规划：LLM-only planner（无规则回退）用 PromptBuilder + PlannerModel 产出结构化 plan；Parser → Normalizer → Validator → 最多一次 Repair。
  7. 计划规范化：strategy 空/未知 → sequential；single 空任务 → 失败；path-aware validator + Agent boundary 二次校验；route_decisions 落库。
  8. HITL（需要时）：main_agent_orchestration 或 REQUIRE_PLAN_CONFIRMATION=true 时进入确认；支持 approve/revise/cancel；跨实例通过 SQL signal + 轮询收敛。
  9. 执行：conversational 直接回复；single 用 SingleExecutor；sequential 用 DAGExecutor（波次/依赖/并行上限）；ordered_parallel 用 SerialExecutor 保持输出顺序。
  10. Agent 调用：Orchestrator 通过 A2A dispatcher 发送任务；附 RunIdentity（run/task/fencing/principal/approval/delegateDepth）与 trace；Agent 返回流式事件。
  11. 回传前端：Executor 产生 AGENT_TURN/消息/任务状态事件；Gateway 映射为 AG-UI 并写公开 journal；前端 reducer 形成消息、工具卡、artifact 卡。
  12. 恢复：断线后前端用 run status/events/resume；Gateway projection worker 从 journal 重建已完成的逐轮助手消息。
POST /api/chat
  → Gateway: validate + requestId + runId + derive path
  → Orchestrator: derive path + validate boundary
  → MainAgent(LLM): plan → parse → normalize → validate (→ repair×1)
  → HITL? approve/revise/cancel (SQL signal)
  → Executor: conversational | single | DAG sequential | serial ordered_parallel
  → A2A Dispatcher → Child Agent(ADK Runner + Tools)
  → AG-UI events → Gateway journal → SSE to Frontend

选择规则

  • Agent 级选择：MainAgent 根据用户目标、Agent 描述、AllowedAgents 边界生成 tasks；越界会被 validator 拒绝。
  • 工具级选择：由 Child Agent 的模型从自己的 tool schema 中选择；平台不提供“模型任意调用任意工具”的全局工具路由。
  • MCP：MCPAdapter 只暴露平台策略白名单中的工具；server annotations 不能授予权限。
  • handoff：handoff_to_agent 受本地 + run plan 双层 allowlist、深度上限、消息/理由/输出上限；它是受控路由，不是自由 swarm。
  • capture/export：web-agent capture_page、markdown-agent markdown.export 调用 Orchestrator 渲染端点；URL 私网拒绝，HTML 模式阻断外部请求。

调用与审批链

  1. 模型产生 tool call；ADK Runner 先判断是否 SideEffectTool。
  2. 只读工具直接执行；副作用工具必须经过 ToolGuard。
  3. Agent 侧 RemoteGuard 调 Orchestrator /tools/authorize，带 run/task/fencing/principal/approval/argsHash。
  4. Orchestrator Tool Broker 校验 approval、预算、fencing、幂等键；写入 dispatch 记录后返回授权。
  5. 工具执行后 /tools/result 落账本；unknown 不自动重试，必须核对真实状态。
  6. 沙箱不可用时 fail-closed，**不会回退到宿主执行**；Docker 真实执行仍未在本机验证。
容易误读：“有工具代码”不等于“工具已开放”。code-agent 写工具、handoff、capture 都是显式 opt-in；默认关闭。MCP adapter 也尚未接入具体 Agent 的审计链路。

07上下文如何压缩

当前不是“让 LLM 自动总结全部历史”，而是多层确定性窗口/截断/召回。各层独立，失败降级。

层机制关键参数/行为状态
前端显示消息窗口默认最近 100 条；Load earlier 每次 +100；不删除服务端历史已实现
Gateway/Orchestrator 请求pinned head+tail保留 head 20 / tail 4，并强制保留 pinnedMessageIds；当前用户消息去重已实现
长期记忆MemoryController recall最多 5 条；过滤 active/过期/超长；按 chars/4 估算 token，受 MaxInjectedTokens 限制；Redis 5m cache已实现
ADK 生成前PruningPlugin启用时 KeepEndsWindow(4,12) + ToolResultTruncator(4000 chars)按 launcher 配置启用
Harness 上下文预算BuildContext默认 MaxChars 120,000；保留 system/pinned、first 3/last 20；tool call/result 成对保留；超预算确定性地 ErrContextTooLarge已实现
自动摘要context-agent已注册 Agent，但未接入主链路的自动压缩；不要宣称“自动摘要压缩已完成”未接入

优先级与降级

  1. system 约束和 pinned 内容不可被静默丢弃；超过 hard limit 直接失败。
  2. 工具调用与结果成对保留；孤立 tool result 被丢弃，不伪造配对。
  3. 记忆召回失败 → 无记忆继续；不使用 stale cache 伪装召回成功。
  4. 预算/上下文超限 → 明确错误，不静默截断关键约束。
P7 方向：在真实 token 计数和压测数据齐备后，再考虑摘要压缩；当前优先保证“可解释、可回放、可失败”。

08MainAgent 不同模式如何切换

先区分两个概念：executionPath 是当前结构化路径；planningMode 是旧的前端请求标记（auto/direct/manual/mention），不再决定后端 planner 模式。Orchestrator 的 planner 始终是 LLM-only。

executionPath触发条件规划/执行HITL
single_chat单 Agent 或单 mention；显式 requestedPath 且解析为 1 个 AgentMainAgent 仍生成 plan；SingleExecutor默认不强制；REQUIRE_PLAN_CONFIRMATION=true 时确认
group_chat多 selectedAgentNames/mentions；显式 requestedPath群计划；sequential 链；发言者 round-robin 或 model按 env；群计划卡可勾选参与者
main_agent_orchestrationauto/字段全空；显式 requestedPathMainAgent 自主选 Agent/任务，受 AllowedAgents 边界始终要求（conversational 除外）

strategy 维度

strategy执行器说明
singleSingleExecutor一个 Agent 处理整个请求
sequentialDAGExecutor按 dependsOn 拓扑波次；无依赖任务可并行；空/未知 strategy 归一到这里
ordered_parallelSerialExecutor为稳定展示顺序保留串行；兼容旧“parallel”映射
conversational直接回复不派发 Agent；免 HITL

群聊内部再分

  • GROUP_CHAT_MAX_ROUNDS：轮数上限（默认 1，最大 5）。
  • GROUP_CHAT_SPEAKER_MODE=round_robin|model：默认 round-robin；model 模式由 MainAgent 逐位选择，越界/缺理由/连续重复/首轮停止 fail-closed，理由写入 route_decisions。
  • HITL：approve 携带确认后的参与者名单；未确认可选成员不会被派发。

HITL 与修订

  • approve：计划继续执行；可选参与者过滤。
  • revise：带反馈重新 plan，revision 递增；不直接执行旧计划。
  • cancel：本地/跨实例写取消请求；待审批和执行中都会收敛。
  • 跨实例：SQL signal + 短轮询；确认/取消不依赖单进程内存。
