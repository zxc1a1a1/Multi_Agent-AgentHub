# 修改前计划规则

## 1. 什么时候必须先计划

以下任务必须先给计划：

- 涉及多个文件；
- 涉及 Skill 重构；
- 涉及代码实现；
- 涉及协议或契约修改；
- 涉及数据库、部署、安全；
- 用户要求先思考；
- 修改范围可能扩大。

## 2. 计划应包含什么

计划应简短但可执行：

```md
## 目标
本轮解决什么问题。

## 依据
参考了哪些用户指定资料。

## 修改范围
会改哪些文件，不会改哪些文件。

## 改动方向
每类文件怎么改。

## 验证方式
如何检查完成质量。
```

## 3. 可以直接执行的情况

用户明确要求：

- “输出文件包”；
- “直接生成”；
- “直接改”；
- “按刚才思路生成”。

这时可以直接执行，但包内必须有 `PATCH_NOTES.md` 和 `MANIFEST.md`。

## 4. 禁止事项

- 不得用计划替代实际交付。
- 不得计划修改用户未授权的目录。
- 不得在计划中引入无关技术栈。
- 不得把未来长期规划写进当前必须执行范围。
